# قرارداد نگهداری نسخهٔ اول محصول

مبنای ثبت: ۲۰ اکتبر ۲۰۲۶؛ نسخهٔ کد ۱٫۲٫۰. وضعیت زنده و اختیار درخواست فعلی بر این سند مقدم‌اند. نام این سند برای حفظ لینک مهارت باقی مانده است.

## منابع و ساخت

منابع import-free در `src/chat.cjs` و `src/catalog.cjs` هستند؛ سازنده آخرین `module.exports` را حذف و منبع آزموده‌شده را در Code node جاسازی می‌کند. پرامپت از `src/system-message.txt` می‌آید. JSONهای `workflows/` خروجی قطعی `node scripts/build-workflow.cjs` هستند؛ آن‌ها را جداگانه دستی ویرایش نکن.

قالب عمومی inactive و فاقد شناسهٔ استقرار و Credentials است. در نامزد خصوصی، شناسهٔ Main و اتصال‌های معتبر حفظ می‌شوند؛ import بدون id ورک‌فلوی تازه می‌سازد. DeepSeek موجود به HTTPهای مدل متصل است؛ همهٔ PostgreSQLها اتصال مستقل چت دارند و Webhook یک Header Auth اختصاصی دارد. شناسه و کلید اتصال‌ها عمومی نیستند.

## گراف واقعی نسخهٔ ۱٫۲

Main شامل ۶۶ نود است: Webhook → اعتبارسنجی ورودی معتبر سروری → admission در PostgreSQL → بارگذاری/پاک‌کردن تاریخچه یا حداکثر چهار دور تماس مدل → ذخیرهٔ پاسخ و آزادکردن lease → Respond to Webhook. سه ابزار ترتیبی در سه دور نخست قابل اجرا هستند؛ دور چهارم `tool_choice=none` است. ساختار ثابت، رزرو و تسویهٔ هر تماس را در خود n8n قابل بررسی می‌کند. نه حلقهٔ نامحدود وجود دارد و نه retry خودکار.

هر دور: آماده‌کردن body محدود → رزرو تراکنشی هزینه → HTTP Request بومی با `deepSeekApi` موجود → خواندن پاسخ/usage → تسویه → پاسخ یا اجرای یک ابزار. ابزار نام/پارامتر محدود دارد و فقط مقصد ثابت provider سایت را می‌خواند. آرگومان نامعتبر، نتیجهٔ خطای ابزار می‌دهد. بیش از یک ابزار در یک پاسخ مدل، پاسخ غیرقابل قبول است و بدون اجرای batch متوقف می‌شود.

مدل `deepseek-flash`، `thinking.type=disabled`، خروجی حداکثر ۱۵۳۶ توکن و timeout هر تماس ۲۵ ثانیه است. API عمومی ابزار timeout ده ثانیه و کل اجرا ۱۵۰ ثانیه دارد. Native Agent قبلی در آزمون واقعی موفق بود؛ تغییر به HTTP برای تسویهٔ قابل اتکای usage تمام تماس‌هاست، نه ادعای ناسازگاری قطعی Agent با DeepSeek.

ورودی Webhook فقط از واسط سروریِ دارای هدر اختصاصی پذیرفته می‌شود. body شامل action و sessionId/clientId هگز ۶۴نویسه‌ای است؛ این شناسه‌ها در کد سایت ساخته می‌شوند و مرورگر حق تعیینشان را ندارد. `sendMessage` حداکثر ۴۰۰۰ نویسه، `loadPreviousSession` و `resetSession` عملیات مجازند. خروجی عمومی فقط response و کد HTTP مربوط است؛ state داخلی و usage به مرورگر نمی‌رود.

## PostgreSQL کاربردی و پول

همهٔ stateها در `project_db.gpante_chat` و با نقش `gpante_chat_app` هستند. دیتابیس داخلی n8n محل ذخیرهٔ تاریخچه یا ledger نیست. migration اولیه `sql/chat.sql` و ارتقاهای `sql/002-public-chat.sql` و `sql/003-conversation-archive.sql` هر کدام یک‌بار اجرا می‌شوند. برگشت JSON، migration یا هزینهٔ انجام‌شده را برنمی‌گرداند.

- `histories`: پیام human/ai با data.content و turn_id؛ پرسش در admission و پاسخ در finish ثبت می‌شود. خواندن کاربر فقط turnهای موفق/قدیمیِ پاک‌نشده و منقضی‌نشده، حداکثر ۱۲ پیام است. زمینهٔ مدل پیش از افزودن پیام جاری به ۲۴۰۰۰ نویسه محدود می‌شود.
- `turns`: زمان اصلی، انقضای کاربر، hidden_at و وضعیت/metadata؛ آرشیو همیشه از created_at تا ۳۰ روز است.
- `policy`: مدت سراسری ۳/۷/۱۵/۳۰ روز، allow_clear و revision؛ تنها API خصوصی مدیریت آن را تغییر می‌دهد.
- `request_counters`: شش پیام/دقیقه و ۳۰ عملیات/دقیقه بر شناسهٔ IP سرور. پاک‌کردن کوکی این شمارنده را بازنشانی نمی‌کند.
- `requests`: lease سه‌دقیقه‌ای، یک درخواست فعال در نشست و دو درخواست سراسری. reset هنگام درخواست فعال رد می‌شود؛ پایان فقط با همان request_id می‌تواند ذخیره کند. reset فقط hidden_at را ثبت می‌کند؛ قرارداد قدیمی بسته است.
- `runtime`: سقف ۲۰۰۰۰۰۰۰۰۰ نانودلار در ماه UTC، enabled و اعتبار تعرفه تا `2026-11-18T00:00:00Z`.
- `model_calls`: کلید یکتای request_id/call_index، ماه رزرو، reserved/settled/burned، هزینه و تعداد توکن؛ بدون متن گفتگو. هر تماس فقط با رزرو تازه مجاز است؛ دور بعد فقط پس از تسویهٔ معتبر دور قبل مجاز است.

رزرو هر تماس ۳۲۰۰۰۰۰۰۰ نانودلار است: context ورودی محافظه‌کارانهٔ ۱۰۴۸۵۷۶ توکن ×۳۰۰ نانودلار + حداکثر ۱۵۳۶ خروجی ×۱۲۰۰ نانودلار، کمتر از رزرو است. منبع [تعرفهٔ رسمی](https://api-docs.deepseek.com/quick_start/pricing/) در تاریخ ثبت بررسی شده است. `prompt_tokens` و `completion_tokens` باید integer نامنفی در این سقف‌ها و `total_tokens` برابر جمعشان باشد. نرخ اوج بدون تخفیف cache حساب می‌شود؛ reasoning_tokens جزئیات خروجی است و دوباره جمع نمی‌شود.

رزرو و تسویه تحت advisory lock کوتاه و هزینه با BIGINT انجام می‌شوند. timeout، قطع اجرا یا usage نامعتبر هرگز refund زمانی ندارند؛ رزروِ قدیمی burned می‌شود ولی هزینه باقی می‌ماند. کمتر از ۰٫۳۲ دلار ظرفیت باقی‌مانده اجازهٔ تماس تازه نمی‌دهد. این سیاست مختص پروژه و ماه رزرو UTC است، نه کل حساب مشترک یا الزاماً دورهٔ صورتحساب ارائه‌دهنده. پیش از تمدید اعتبار نرخ یا عوض‌کردن مدل، context، قیمت و رزرو را دوباره تطبیق بده؛ به‌روزکردن صرف تاریخ کافی نیست.

Retention دو نود دارد: Schedule Trigger ساعتی → `gpante_chat.cleanup()`. حذف تاریخچهٔ بیش از۳۰ روز، شمارنده‌های قدیمی و leaseهای قدیمی مستقل از ترافیک انجام می‌شود؛ ledger حذف یا با انقضا refund نمی‌شود. در ۲۰ اکتبر با MCP رسمی منتشر و active=true بازخوانی شد. اجرای صریح نسخهٔ منتشرشده با mode=trigger موفق بود؛ fixture منقضی حذف و fixture جدید حفظ شد و دفتر مالی تغییر نکرد. آن آزمون صریح به‌تنهایی شاهد نوبت ساعت نبود؛ اجرای طبیعی نیز در مرحلهٔ راه‌اندازی تولید مشاهده شد. آخرین وضعیت نگهداری را در هر ورود از executions بررسی کن.

فقط Retention نتیجه و خطای اجرای تولید را ذخیره می‌کند (`saveDataSuccessExecution=all` و `saveDataErrorExecution=all`) تا نگهداری قابل پیگیری باشد؛ دادهٔ این گراف زمان trigger و تعداد حذف است و پیام گفتگو را بارگذاری نمی‌کند. Main همچنان ذخیرهٔ اجرای خام موفق/ناموفق/دستی را خاموش نگه می‌دارد. قالب عمومی Retention عمداً inactive و بدون Credentials است؛ وضعیت انتشار را از قالب import نتیجه نگیر.

## قرارداد provider و کد سایت

منبع ابزارها `https://gpante.com/wp-json/gpante-support/v1/products` و `/knowledge` است. منبع canonical اکنون افزونهٔ `wordpress-plugin/gpante-support-chat/` نسخهٔ ۰٫۱٫۱ است؛ `integration/wordpress` راهنما، loader سازگاری و embed تولیدی را نگه می‌دارد. اتصال تولید با درخواست بعدی کاربر مجاز و بررسی شد؛ نتیجه در [گزارش تولید](../../../../docs/production-readiness.md) است. اجرای PHP سمت سرور لازم است؛ درج JavaScript یا HTML به‌تنهایی واسط امن یا provider را ایجاد نمی‌کند. قالب عمومی عمداً inactive است و وضعیت فعال را باید از سرویس خواند.

provider محصول publish، بدون رمز، product اصلی و visible/catalog/search را می‌پذیرد؛ hidden، variation، خصوصی و محافظت‌شده رد می‌شوند. جزئیات همان فیلتر را دارد. Schema و ترتیب قیمت بومی WooCommerce بازاستفاده شده‌اند و نبود قابلیت لازم خطا می‌دهد. رکوردهای stdClass قیمت، ویژگی، term و تصویر پیش از انتخاب فیلدهای عمومی به آرایه تبدیل می‌شوند. قیمت، ویژگی‌ها و لینک‌ها allowlist دارند؛ فایل و دادهٔ مشتری هرگز خوانده نمی‌شوند.

فیلترها AND هستند. normalization فارسی/عربی و alias کنترل‌شدهٔ باکس/جعبه وجود دارد. «MDF یا پلکسی» با شاهد نام term واقعی، برای MDF و پلکسی سازگار است؛ ترکیب «و» به تک‌متریال تبدیل نمی‌شود. `sort=price_asc` روی کل نتایج فیلترشده در منبع اعمال می‌شود؛ یک صفحهٔ relevance شاهد ارزان‌ترین کل کاتالوگ نیست. هر صفحه پنج محصول و حداکثر ۱۶۰۰۰ نویسه خروجی ابزار دارد؛ بزرگی بیش از سقف خطای صریح است و نتایج به‌صورت خاموش حذف نمی‌شوند.

کد واسط کوکی امضاشدهٔ ۳۰روزه، HTTPS، Origin دقیق و Fetch Metadata را بررسی می‌کند و IP را از REMOTE_ADDR با HMAC می‌سازد. هدرهای دلخواه forwarded معتبر نیستند؛ پراکسی، cookie/cache و timeout باید روی سرور واقعی بررسی شوند. کلید خصوصی فقط در تنظیم سروری و Credential n8n می‌ماند. منبع کنترل لینک مرورگر مستقل است؛ تفاوت قرارداد آن با ابزار/پاسخ مدل دلیل ادغام‌نکردن اعتبارسنج‌هاست.

## بررسی و عملیات

`node --test tests/*.test.cjs`، PHP lint، `php tests/widget-bridge.php` و `php tests/catalog-query.php` آزمون‌های محلی‌اند. `tests/money-concurrency.py --user <maintenance-user>` آزمون دو رزرو هم‌زمان و جداسازی ماه روی PostgreSQL واقعی است؛ Main باید غیرفعال باشد و کاربر اجرا مجوز نگهداری schema چت داشته باشد. این تست بودجه را موقتاً پایین می‌آورد و فقط رزروهای fixture معلومِ بدون HTTP را در finally پاک می‌کند؛ آن را الگوی refund رزرو نامعلوم مدل نکن. `tests/database.sql` با rollback اجرا می‌شود و برای محیط Main غیرفعال نوشته شده است. `scripts/validate-native.cjs` روی کپی خصوصیِ دارای اتصال، activation نصب‌شده، SDK strict و کامپایل Code را بررسی می‌کند. تست محلی provider جای WooCommerce واقعی نیست.

در CLI، exit code یا خروجی خالی کافی نیست؛ `status`، resultData.error و خطای هر نود بررسی شوند. اجرای آزمایشی مجزا `N8N_LOG_OUTPUT=console` و broker port جدا داشت. نتیجهٔ خام و resume token خصوصی‌اند. ورک‌فلوی Validation پس از آزمون با import رسمی isArchived=true آرشیو می‌شود. API key از دیتابیس استخراج نشد.

CLI `publish:workflow` نصب‌شده اعلام می‌کند تغییر انتشار روی process در حال اجرا تا restart اثر نمی‌کند. MCP رسمی همین instance مسیر انتشار مؤثر بر process جاری را فراهم کرد؛ Retention با `publish_workflow` منتشر و اجرای واقعی نسخهٔ منتشرشده با `execute_workflow(executionMode=production)` بررسی شد. سرویس restart نشد. `n8n execute --id` روی گرافی که فقط Schedule Trigger دارد با «Missing node to start execution» متوقف می‌شود؛ این خطا به‌تنهایی خرابی Schedule Trigger نیست. برای آزمون آن از مسیر رسمی trigger استفاده کن. به‌علت `saveManualExecutions=false`، اجرای دستی موفق ممکن است در history باقی نماند؛ نبود history را موفقیت یا شکست اجرا تلقی نکن.

## مدیریت آرشیو

Main از `admit_v3` / `finish_v3` استفاده می‌کند؛ یک پرسش پذیرفته‌شده حتی در شکست مدل باقی می‌ماند. Admin پنج نود، Header Auth مستقل و نقش محدود به `admin_api(jsonb)` دارد؛ عملیات ثابت getPolicy/setPolicy/listSessions/getSession. صفحه‌های ۲۰تایی آرشیو از زمینهٔ ۱۲پیامی مستقل‌اند. Main و Admin اجرای خام ذخیره نمی‌کنند. جزئیات و محدودیت‌ها در [راهنمای آرشیو](../../../../docs/conversation-archive.md) هستند؛ وضعیت انتشار زنده باید جدا خوانده شود.
